# GitHub triage

Run only when explicitly invoked. Infer the repository from its Git remote and use the
available GitHub tooling. Triage existing issues; `to-issues` creates a planned backlog.
Use the user's existing authorization for edits. Recommendations alone do not authorize
posting comments, relabeling, or closing issues.

Begin each new comment with the disclosure below. In a task body, keep the required
Task contract or Source plan block first, then place the disclosure before the task prose:

> *This was generated by AI during triage.*

When updating an existing issue, preserve the reporter's account and mark the section you
authored. Give evidence and a reason for each state change.

## Labels and transitions

Keep one category (`bug` or `enhancement`) and one state label. Preserve unrelated labels,
including `wave-N`. Explain unfamiliar or conflicting states; use an explicit user choice
to resolve them, otherwise ask only for the unresolved choice.

| State | Meaning | Normal next states |
|---|---|---|
| no state label | Not yet assessed, even if other labels exist | needs-triage, afk, hitl, wontfix |
| needs-triage | Needs a maintainer decision | needs-info, afk, hitl, wontfix |
| needs-info | Waiting for information | needs-triage when a relevant reply arrives |
| afk | Away from keyboard: ready for an agent to implement unattended | Maintainer-directed change |
| hitl | Human in the loop: needs user participation | Maintainer-directed change |
| wontfix | Will not be implemented; close with a reason | Maintainer-directed reconsideration |

The maintainer can override the normal path. Apply an already specified choice without
another interview; explain the edits. A label alone does not make a task runnable: a
governed task still needs a current contract and usable acceptance criteria.

## Review the queue or one issue

For an overview, retrieve the complete requested set, or report the limit and what remains
unexamined. Show issues with no state, `needs-triage`, and `needs-info` with replies newer
than the last triage notes. Group counts and list oldest first, with number, title, age,
and a short summary. Let the user choose unless they already named the scope.

For each chosen issue:

1. Read its body, comments, labels, and prior triage notes. Inspect related code and
   requirements. Check [recorded scope decisions](OUT-OF-SCOPE.md).
2. For a bug, attempt a reproduction and report what happened. Missing details may justify
   `needs-info`; a failed attempt does not prove there is no bug.
3. Recommend category and state with evidence. Ask only for missing decisions or facts;
   reuse answers already recorded in the discussion.
4. Prepare the outcome below, then apply it within the user's authorization.

## Record the outcome

- **afk / hitl:** update the issue body using [the shared task format](AGENT-BRIEF.md).
  Record why user participation is needed for `hitl`. Keep the task instructions in the
  body; comments explain decisions and provide context.
- **needs-info:** post short triage notes with **Established** and **Still needed** lists.
  Preserve resolved facts so the next session can resume without repeating questions.
- **wontfix:** explain the reason and close. For a durable rejected feature, record the
  reason as described in [scope decisions](OUT-OF-SCOPE.md). Duplicates link to the existing
  issue; temporary lack of time is a deferral, not a permanent scope decision.
- **needs-triage:** apply the label; record partial findings only when useful.

Before marking work ready, check its source requirements and acceptance criteria. If
`definitions/spec.md` governs the work, require the current `Task contract` described in
[amend mode](../../docs/amend-mode.md). Missing or outdated contracts stay held for
`to-issues` reconciliation; an `afk` override does not bypass that check. If no governing
specification exists, a self-contained legacy task may proceed without a contract.

Report the issues changed, reasons, and unresolved questions. Do not create another task
ledger or repeat the whole discussion in the report.
